THE FOOTGUN

Looks like React. Crashes like Lynx.

This is valid React. It's also four runtime bugs that React tooling cannot see. The compiler accepts it. The bundler ships it. It only fails on a real device — silently.

src/Counter.tsx · what the engineer wrotelooks fine ✓
import { useState, useRef } from "@lynx-js/react";

export const Counter = () => {
  const [count, setCount] = useState(0);

  function onPress() {
    "main thread";
    setCount(count + 1);           // silent no-op
    const r = useRef(null);      // wrong-thread ref
    await fetch("/api");          // no microtasks here
  }

  if (typeof window !== "undefined") { ... } // no DOM

  return (
    <view>
      <text onClick={onPress}>tap</text>
    </view>
  );
};
ERROR  4 dual-thread bugs in 12 lines
  • setCount on main thread — the React state setter lives on the background thread. Main-thread call returns; state never updates.
  • useRef on main thread — returns a background-thread ref. .current never reflects what main-thread render sees.
  • await + async — main thread has no microtask scheduler. The Promise is dropped on the floor.
  • window / document — DOM globals are undefined under Lynx; you'll crash on first access.
  • onClick on <text> — Lynx host elements use bindtap/catchtap. The handler never fires.

None of this fails any check today. No type error. No lint warning. No build error. The app boots and silently misbehaves.

WHAT WE PORTED TO

ReactLynx — same React, different runtime.

ReactLynx = React semantics (hooks, render, JSX) + custom host elements (<view>, <text>) + a dual-thread runtime + custom events (bindtap) + a Lynx CSS subset + Rspeedy (Rsbuild) tooling. Most footguns come from the runtime split.

MAIN THREAD

UI · sync · no microtasks

  • Renders JSX, dispatches sync UI updates
  • No DOM, no window, no scheduler
  • Opted in with the 'main thread' directive
  • Cannot async/await · cannot construct Promise
  • Setters from useState live on background
⇄
runOnBackground
runOnMainThread
BACKGROUND THREAD

State · effects · I/O

  • Runs useEffect, useLayoutEffect, useImperativeHandle
  • Event handlers (bindtap, catchtap) by default
  • Native module calls, network, timers
  • Full microtask scheduler, Promises work
  • Owns React's state graph

The mental model that broke every check. A React-on-DOM linter assumes one runtime, one set of globals, one set of event names. ReactLynx has two runtimes, no DOM globals, and a separate event vocabulary — but the React parts (hooks, render, props) are identical. So most checks should still fire; a handful must flip off; and a new family must be added for the boundary.

WHAT'S ACTUALLY DIFFERENT

Four shifts. Everything else stays React.

① No DOM. No Web globals.

window, document, localStorage, navigator are undefined under Lynx. Lift assumptions caught by rl-no-dom-globals; silence 36 a11y rules that bake in HTML/ARIA semantics.

rl-no-dom-globals · 94 LOC · 17 tests

② Custom host elements + events

JSX lowercase tags <view>, <text>, <scroll-view>, <list>… and bindtap/catchtap instead of onClick. no-unknown-property disabled for them; rl-no-onclick-on-builtin catches the regression.

rl-no-onclick-on-builtin · 49 LOC · 14 tests

③ Dual-thread runtime

The 'main thread' directive splits execution. Four rules guard the boundary: no async, no useRef (use useMainThreadRef), no direct setter call, no background-only API in render.

rl-main-thread-* · 438 LOC · 43 tests

④ Engine packages ship in lockstep

The trio @lynx-js/react + @lynx-js/rspeedy + @lynx-js/react-rsbuild-plugin must move together. Partial installs fail at first render with errors that look like config bugs. Hard-error before that happens.

check-engine-versions · check-rl2-rl3-migration-debt

What stayed unchanged (and why that's the point)

  • Hooks rules of React — render model is identical, rules-of-hooks fires the same way under Lynx.
  • Render-perf rules (rerender-functional-setstate, prefer-module-scope-pure-function, …) — referential equality & component shape concerns apply unchanged.
  • State & effects bucket — 63 rules, all still meaningful on dual-thread code.
  • JS-perf / bundle-size / architecture — orthogonal to runtime, all preserved.

HARNESS ENGINEERING

The deck is the demo. The harness is the product.

This branch was built inside a Claude Code harness with a small, explicit set of process disciplines. None of it is novel; the value is in making the principles load-bearing by encoding them as durable artifacts — CLAUDE.md rules, a PRD, a Goal hook, agentic Skills.

PRINCIPLE 01

"说不清解决什么问题的改动，就不该做。"

Every milestone was preceded by a US (User Story) naming the concrete bug it prevents. No "more robust", no "feels cleaner". If you can't name the runtime crash, you don't ship the rule.

M2 audit: each of 46 candidate rules → (a) keep, (b) disable, (c) defer — with a one-line reason.
PRINCIPLE 02

Don't mechanically port upstream patterns — verify the premise.

The skill's detect-background-only rule was ported as rl-no-background-only-api-in-render. But the other three skill rules were considered and deferred: same intent, different cost/value at static-analysis depth.

M6 PRD names every skill rule + why it's in/out. No silent omissions.
PRINCIPLE 03

Don't classify any failure as "pre-existing" by gut.

38 plugin tests were red. Stashed the branch, re-ran on the base ref, confirmed identical 38 failures. Only then triaged as pre-existing.

git stash && pnpm test && git stash pop — encoded as a habit, not a slogan.
PRINCIPLE 04

Compile passing ≠ usable. Run the binary.

End-to-end run of the built CLI against the fixture exposed an audit gap (no-unknown-property flagging bindtap) that the unit suite missed. The gap is now a pinned regression test.

api/tests/reactlynx-fixture-regression.test.ts — 5 tests pin the no-false-positive contract.
PRINCIPLE 05

The PRD is the harness's planning surface.

tasks/prd-reactlynx-checks.md is 554 lines: every US, every decision, every milestone. The agent reads it in to load context; the human reads it to spot-check. Same artifact, two consumers.

M0 ✓ M1 ✓ M2 ✓ M3 ✓ M4 ✓ M5 ✓ M6 ✓ — checked into git, not into memory.
PRINCIPLE 06

Skills + static rules converge on layered checks.

Each layer has a different failure mode: static rules verify shapes, skills narrate fixes, runtime smoke observes behavior. The PRD's appendix sketches a shared contract so a new footgun is a coordinated 3-layer update, not a triple-write.

docs/REACTLYNX_RULES.md — every rl-* rule paired with its sibling skill rule.

Net: A senior IC could have written this branch in a week. The harness turned that week into a reproducible, reviewable, regression-pinned process — one where the next framework target (Solid? React-Server? Lynx-Web?) follows the same 6-milestone shape, the same PRD discipline, and the same end-to-end fixture-run gate.
